## 1. 完全削除APIがゴミ箱を経由していない生タスクも削除できる

**何が問題か**

画面とコメント上の契約は「通常削除はゴミ箱への論理削除、完全削除はゴミ箱画面からだけ」ですが、`DELETE /api/trash/:id` のDB処理は `id` しか条件にしていません。対象がゴミ箱にあるかを確認しないため、ボード上の生タスクIDを直接指定すると、ゴミ箱を経由せず即座に実体が消えます。

この呼び出しでは `broadcastBoard()` も行わないため、DBから完全削除された後も、接続中の画面には次の更新イベントまでカードが残ります。利用者は削除に気づかず、そのカードを操作して初めて404になる可能性があります。

DELETEの条件へ `AND trashed_at IS NOT NULL` を足し、該当しない場合は409または404を返すだけで局所的に修正できます。

**再現条件**

1. Todoタスクを1件作成し、IDを確認する。
2. 通常の `DELETE /api/tasks/<id>` は呼ばず、直接 `DELETE /api/trash/<id>` を送る。
3. 200 `{ "ok": true }` が返る。
4. `GET /api/tasks/<id>` は404となり、ゴミ箱にも残っていないため復元できない。
5. 既に開いていたボードでは、別の更新イベントが来るまでカードが表示されたままになる。

## 2. 不正なmembersを含むプロジェクト作成・更新が途中まで適用される

**何が問題か**

プロジェクトAPIは `members` が配列かだけを確認し、各要素が文字列かを確認しません。DB層は各要素へ直接 `.trim()` を呼ぶため、数値やnullが1つ混ざると例外になります。

新規作成では、その検証より先に管理DBのプロジェクト行を作成し、プロジェクトDBファイルも開いてスキーマを作ります。その後に例外となるため、APIは500を返すのにプロジェクト一覧には作成途中のプロジェクトが残り、既定の前提情報も初期化されません。更新では、名前変更を先に適用してからメンバー処理で失敗するため、500なのに名前だけ変わる部分適用になります。

ハンドラー冒頭で `members.every((x) => typeof x === "string")` を確認して400を返せば、作成・更新のどちらも小さな変更で防げます。

**再現条件**

新規作成では次を送ります。

```http
POST /api/projects
Content-Type: application/json

{"name":"途中まで作られる","members":["zio",1]}
```

レスポンスは500になりますが、その後 `GET /api/projects` を呼ぶと「途中まで作られる」が残っています。

更新では次を送ります。

```http
PATCH /api/projects/2
Content-Type: application/json

{"name":"名前だけ変わる","members":[null]}
```

レスポンスは500ですが、再取得すると名前だけが変更されています。

## 3. URLで別プロジェクトを開いてもサーバー既定プロジェクトは切り替わらず、削除ボタンが必ず失敗する

**何が問題か**

現在のUIのプロジェクト切替はURLを `/p/<id>` へ変えるだけで、サーバーの `project.active` は変更しません。これは複数タブを独立させる設計として妥当ですが、削除可否だけは両者を混同しています。

画面は「URLで表示中でなければ削除ボタンを出す」のに対し、サーバーは「`project.active` なら削除拒否」と判定します。例えば既定プロジェクトAからBを開くと、Bの設定画面にはAの削除ボタンが表示されますが、押すと「表示中のプロジェクトは削除できません」と400になります。実際に表示中なのはBであり、UIから `activateProject()` を呼ぶ経路も無いため、AはUI操作だけでは削除できません。

少なくとも削除ボタンの条件を `!p.active` にも合わせれば誤った操作は出なくなります。既定プロジェクト自体も削除可能にするなら、削除時に残る別プロジェクトへ `project.active` を付け替えてから退避する方法が局所的です。

**再現条件**

1. 既定（active）プロジェクトAがある状態でプロジェクトBを作成する。
2. 「開く」またはヘッダー選択からBの `/p/<BのID>` へ移動する。
3. Bの設定画面で、Aに「削除」ボタンが表示されることを確認する。
4. Aの「削除」を押す。
5. サーバーはAをactiveと判定し、「表示中のプロジェクトは削除できません」と400を返す。UI上でAを非activeにする手段はない。
