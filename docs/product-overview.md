## 1. 一行で言うと

**会話がそのままタスク管理になる。** かんばんとチャットの二層UIで、タスクの登録から完了検収までを会話で回す。AIは登録も更新も並べ替えも確定まで進めるが、**Doneだけは人間の検収を必ず通る**(ボードからの退場と要約の組み直しを伴う、影響の大きい操作だから)。

MCPで繋いだときの言い方だと、**やりたいことを番号で言えるようになる外部記憶**。詳しくは §3-⑧。

---

## 2. 何を解いているのか

タスク管理ツールの本当のコストは「入力」ではなく「**書き写し**」にある。

打ち合わせやチャットで決まったことを、あとからボードに転記する。転記の過程で「なぜそう決めたか」が落ちる。落ちた文脈は誰も復元できないので、3日後に「これ何だっけ」が始まる。

ChatBanは転記工程そのものを消す。**話した場所がそのままボードになる**ので、決定と記録の間に距離がない。そして落ちがちな「なぜ」を、タスクの経緯メモとして構造的に持ち続ける。

一方で、AIにタスク管理を任せる怖さは「勝手に動く」ことにある。だが**確認を挟む価値があるのは影響の大きい操作だけ**なので、人間のゲートは入口ではなく出口に置いた。登録も更新も並べ替えもAIが確定まで進め、Doneへの退場だけは人間が押す。この非対称が製品の背骨(→ §3-③)。

## 3. 売り (差別化ポイント)

### ① 新規作成フォームが存在しない

タスクを作る手段はチャットだけ。「ログイン画面のバグ直さないと」と話すとカードが生える。スクショやPDFを貼って相談することもできる。

**原本はどこにも保存しない。** AIが読んだ「意味」だけが経緯メモに残る。物置にしないことで、公開リポジトリへの混入リスクがゼロになる副次効果もある。

### ② Doneが「置き場」ではなく「蒸留装置」

普通のかんばんでDone列は溜まる一方で、溜まるほど読まれなくなる。ChatBanでは検収されたタスクは即アーカイブされ、AIが要約カードに畳む。

**実測: 89タスク → 5要素。** 却下した(=やらないと決めた)タスクも理由ごと要約に残るので、「決めたという仕事」が消えない。再オープンすると要約から言及が消える(常にボードの真実に追従する)。

### ③ 人間のゲートは入口ではなく出口に置く

| 局面 | AIの役割 | 人間の役割 | なぜそこか |
|---|---|---|---|
| 登録・更新・並べ替え | **判断して確定** | 見て、違えば直す | 後から変えられる。確認を挟むより速い |
| 完了 | Reviewに置く + エビデンスを経緯メモに貼る | 検収チェック → 一括Done | **ボードから退場して要約に畳まれる。影響が大きい** |

再オープンはできる(要約から言及が消え、カードが戻る)。**取り返しがつかないのではなく、影響範囲が違う** — 登録や並べ替えの直しはカード1枚で閉じるが、Doneは退場と要約の組み直しを伴う。以前は割り振りにも承認UIを置いていたが、外した(#128)。**確認を挟む価値があるのは、そこまで影響の大きい操作だけ**という整理に落ち着いた(割り振り機能そのものは #179 で廃止し、個人利用に特化した)。

**チャットからDoneへ直行する経路はコードレベルで存在しない**(`update_tasks`がdone指定を強制的にreviewへ変換する)。プロンプトの禁止ルールは拡大解釈で漏れるが、ツール契約は漏れない。

### ④ Review列がAIの検証ワークリストになる

「Reviewに溜まっているものを動作確認して、スクショをエビデンスとして経緯メモに貼っておいて」がそのまま指示になる。人間は根拠を見て✓を押すだけ。**AIに働かせる場所と人間が判断する場所が、列として分離している。**

### ⑤ 経緯が残り、しかも読まれる

「なぜそう決めたか」がタスクの経緯メモに貯まります。経緯欄自体はどのツールにもありますが、
**埋まらないのが普通**です。書く動機が本人になく、読み手が「未来の誰か」だから。

変わったのは書く手間が消えたことより、**必ず読む相手ができた**ことです。
次のセッションのAIが実際に読みます:

- 「なんでDB分けたんだっけ?」→ 検索して当時の判断(「#IDが会話の語彙だから」)を答える
- Doneの要約にも「並べ替えはソートキー方式を捨て、LLMが決めた順番を受け取る方式にした」と残る
- コードを読んでも分からない「捨てた案」が残る

### ⑥ MCPサーバー内蔵 — BYO Agent

内蔵チャットは安いモデルで定型操作に徹する。横断的な設計判断や実装は、`POST /mcp/<projectId>` 経由で**使う人自身のエージェント**(Claude Code等)に委ねる(プロジェクトを指定しない `POST /mcp` は400で拒否する — 接続URLで書き込み先が固定されるのが設計の要)。モデルの財布も裁量も持ち込み。

この設計は実証済み: **ChatBan自体の開発タスクが、ChatBanのボードでMCP経由で管理されている。**

### ⑦ 「作らない判断」が製品の一部として記録される

要望が来たら断ることもある。断った理由は却下タスクとして要約に蒸留される。実測でチャット自身が「#19で決定済みです」と根拠付きで断り、代替案3つを提示した。**断り方も製品仕様。**

### ⑧ 索引付きの外部記憶として働く

⑥の裏返し。MCPで繋いだとき、ボードは**エージェントの外部記憶**になる。素朴な単一Markdownメモに積む記憶や、埋め込み検索だけで引く記憶との差は、**索引が最初から付いていること**。

| 索引 | 実体 |
|---|---|
| 状態 | todo / inprogress / review / done |
| プロジェクト | SQLiteファイルの物理分割(最上位の索引) |
| 時間 (短期) | `sync_board` の同期トークン差分(前回から何が変わったか) |
| 粒度 | Done要約カード(古い記憶は圧縮された形で引ける) |

時間の索引は**短期の差分に限る**。比較用スナップショットはプロセスメモリ上で保持60分・1プロジェクト32件までで、再起動すると失効する(失効時と、変更が40件を超えたときはエラーにせず、理由を添えて全件を返す)。永続的な変更履歴ではないし、任意の過去時点を遡って引く索引でもない。

この見方だと、**カラム移動は索引の更新、検収は「この記憶は確定した」というマーク付け、蒸留は記憶の階層化**になる。つまりChatBanは「かんばんに記憶が付いている」のではなく、**「索引済み外部記憶に、かんばんというUIが付いている」**。

**索引の価値は「探せる」ではなく「指させる」。**「#10がやりたい」— 接続先プロジェクト内で一意な3文字のID、それだけで意思決定が完結する(IDは各プロジェクトで `#1` から振られるので、一意なのはMCPの接続先の中)。素の記憶だと「ほら、あの、先週話した公開まわりのやつ……」と記憶の再記述から始まり、AI側も確率的な想起をする。効能は二方向:

- **人間→AI**: 意図の表明が安い。意思決定の語彙がIDで済む
- **AI→データ**: 引くのが安くて正確。ベクトル検索の「たぶんこれ」ではなく主キーの「これ」

実運用ではAI側も「#131 #132 #133 として振りました」とIDで返す。**会話の中を安定したポインタが行き交い、板が人間とAIの共有アドレス空間になる。**「板に話しかけるチャット」が成立するのも、話しかける対象の全オブジェクトに番地が振ってあるからだと言える(番地のない記憶に話しかけると、毎回住所の説明から始まる)。トークン経済としても、参照がIDに圧縮されるぶん往復のたびに文脈を再送しなくていい — `sync_board` の差分と合わせて「必要な記憶だけが、最小のトークンで、正確に卓上にある」。

#### なぜ人間が日常的に板を見る運用でこそ効くのか

効いている理由は3つに分解でき、**2つは狙って作ったものではない**:

| 効いていること | 由来 | 強度 |
|---|---|---|
| 索引が付く | かんばんという形式。設計として狙った | コードが保証する |
| **索引が腐りにくい** | 人間が自分の都合で毎日見るから。棚ぼた | 運用がもたらす |
| **記憶に確定度がある** | 検収ゲート(#57)。別の理由で入れたものが効いた。棚ぼた | コードが保証する(`checked_at`) |

記憶ファイルは書き手も読み手もAIなので、腐っても誰も気づかない(腐ったことすら分からない)。ChatBanの索引が保たれるのは、**記憶の保守コストを人間が別の動機で払っている**から。UIの要求(人間が一目で状態を見たい)が、そのまま良い索引を強制している。ただしこれは**運用の性質であって不変条件ではない** — 人間が見なくなれば同じように腐る。

そしてエージェントがタスクを取って自己申告で閉じるキュー型では、**「人間が確かめた」と「まだAIの主張」の区別が付かない**。ChatBanは人間が検収したものだけがDoneに入るので、記憶に二層がある。ここで保証されるのは**検収したという事実**であって、書かれた内容が客観的に正しいことではない(人間は間違えるし、再オープンもできる)。

**帰結1**: human-in-the-loop の位置づけが変わる。安全側の制約(足枷)であるだけでなく、**記憶の品質を担保する装置**でもある。守りの説明が攻めの説明にもなる。
**帰結2 (設計のガードレール)**: 自律実行の方向に寄せると、人間が見なくなった瞬間に棚ぼた2つが両方消え、ただのディスパッチャーに落ちる。**足すなら「人間が見る理由」を減らさない形で。**

なお汎用の記憶MCPとは競合ではなく**役割分担**になる。構造化できる記憶(作業・決定・進行)はChatBanへ、構造化前の雑多な気づきは素朴メモへ。熟したらタスク化して移す。

## 4. 画面構成

```
┌─ ボード (かんばん4列固定) ────────────────────────┐
│  Todo    InProgress    Review      Done(要約カード) │
│                        ↑検収チェック   ↑D&D禁止      │
├──────────────────────────────────────────────────┤
│  チャット (常設。折りたためない = アイデンティティ)  │
│   起動時: AI提案チップ (ボード文脈から最大3つ)      │
│   + ボタン=ファイル添付 / 🆕=新しい会話            │
└──────────────────────────────────────────────────┘
      タスクカードをクリック → 詳細パネル (タスク専用チャット)

タブ: ボード / 📋前提 / 🗑ゴミ箱 / ⚙設定   (📊コストと📜監査は #181 で撤去)
ヘッダー: プロジェクト切替 (URL /p/<id> が表示中のプロジェクトを持つ)
```

- **タスク属性は最低限**: 優先度なし・タグなし・サブタスクなし。「チャットで言えば済むものは属性にしない」が判断基準
- あるのは: status(固定4列) / **summary**(いまどうなっているか) / 経緯メモ / due / 依存(blocked_by) / rejected
- 属性は減らす方向にも動かす: 「今回やる/後で」を表す lane(demo/later) は廃止した(#107)。他ツールでも列やスプリントで表すもので、フィールドは代用でしかなく、実データでも47件中1件しか使われていなかった。並び順で表現できる。担当者(assignee / assign_reason)も同じく廃止した(#179) — 一人で回すなら空欄が正常な状態で、「空欄には2種類ある」を説明し続けるほうが高くつく
- **4列は同じ重みではない**: Todo/Inprogressは「人間がステータスを気にしたいときに振り分ける箱」程度の緩い扱い。Reviewは退場ゲート、Doneは人間の検収のみ
- 属性が少ないほどLLMが迷わない ＝ **LLM親和性を優先した非正規化**

## 5. コストの話 (これが技術的な芯)

> **計測の仕組みは #181 で撤去しました。**単価・モデルカタログ・残高・トークン集計と
> 📊コストタブ・📜監査タブは、ハッカソンの審査観点に答えるための実装でした。
> **以下の数字はその期間の実測で、いま画面から再現することはできません** (一次データは
> [cost-engineering-log.md](cost-engineering-log.md) に残しています)。
> 蒸留の設計そのものは製品に残っており、個人利用ではトークンとレイテンシが
> `backend/logs/` に出ていれば足ります。

2日間のフル開発 + ドッグフーディングで:

| 指標 | 実測 |
|---|---|
| LLM呼び出し | **562回** |
| トークン | 入力 2.60M / 出力 0.25M |
| うちキャッシュヒット | **1.26M** (入力の48%) |
| 実請求額 | **$3.66** |
| チャット1ターン | 0.2〜0.3円 / 0.9〜1.5秒 |

初期は1ターン8円かかっていた。0.2円まで落ちたのは偶然ではなく、**同じ蒸留原理を4箇所に適用した結果**:

| 適用先 | やったこと |
|---|---|
| Doneアーカイブ | 完了タスクを要約カードに畳む |
| ボード常駐情報 | 全フィールド → 索引のみ + 詳細は遅延取得 |
| システムプロンプト | 基準スナップショット + 差分イベント追記、TTL切れで再ベースライン |
| 添付ファイル | 原本を捨て、AIが読んだ意味だけ残す |

> **「生データは保持する。文脈に載せるものは蒸留する。蒸留のタイミングはコスト境界で決める」**

### キャッシュを効かせる条件は2つセット

1. **プレフィックスをバイト単位で安定させる** — 状態を差分イベントとして後置する
2. **モデルIDを固定する** — キャッシュの実体はそのモデルのKVキャッシュなので、ルーティング先が変われば原理的に全ミス

これが「対話はモデル固定・非同期の要約はルーティング委任」という用途別戦略の根拠になっている。応答性の観点(autoは103秒を引く回があった)と、キャッシュの原理の観点の**2本立て**。

### 用途別モデル戦略

| 用途 | モデル | 理由 | 実測 |
|---|---|---|---|
| 対話 (chat/suggest) | `openai/gpt-5.4-mini` 固定 | 応答速度が生命線 + 自動キャッシュ | 482回 / 平均1.3秒 |
| 要約分解 | `orcarouter/auto` → `openai/gpt-5.6-luna` | 品質が肝・非同期だが、autoは遅すぎた | 40〜80秒 → 4〜12秒 |
| 定型 | `orcarouter/fusion-mini` → `openai/gpt-5.6-luna` | 短いラベル生成に思考は要らない | 29.7秒 → 数秒 |

**モデルIDを1行書き換えるだけで比較実験ができる**ため、この用途別最適化を半日で実測ベースで決められた。
当初は「品質が肝の要約はルーティングに委任」としていたが、**実測では遅さの正体が思考トークンで、
行き先が毎回変わること自体が体験を不安定にしていた**ので、全部固定に倒した。
実行時に切り替える⚙設定タブも用意していたが、#181 で撤去した (供給元が単価つきカタログだった)。

### 事業として見ると

チャット1ターン3〜8円(最適化前)はチーム月1〜2万円規模。一般的なタスク管理SaaSが月$16程度であることを踏まえると、**LLM原価がSaaS価格を食い破りかねないカテゴリ**。コスト工学は「最適化」ではなく**事業成立条件**だった。

## 6. 技術スタック

| 層 | 技術 | 選定理由 |
|---|---|---|
| フロント | Vite + React 19 + TS + Tailwind v4 + dnd-kit | AIで書きやすい + HMRの応答性 |
| リアルタイム | Socket.IO | ボード変更・ツール進捗・要約再生成の逐次配信 |
| バック | Express + better-sqlite3 (プロジェクトごとに1ファイル) | 最小構成、同期APIで簡潔 |
| LLM | OpenAI SDK → **OrcaRouter** | OpenAI互換。`ORCA_BASE_URL` 1行でプロバイダ差し替え |
| 外部連携 | MCP (Streamable HTTP) | Claude Code等からボードを直接操作 |
| テスト | Playwright E2E | 専用ポート/DBで開発サーバーと共存 |

LLM呼び出しは `backend/logs/chatban-YYYY-MM-DD.log` に1行ずつ残る(`tokens=8208/23 cached=3200 1555ms`)。かつては `llm_calls` テーブルへの打刻と📜監査タブからの全ログExportがあったが、#181 で撤去した。会話・タスク・要約カードは `query_log` (読み取り専用SQL) で引ける。
