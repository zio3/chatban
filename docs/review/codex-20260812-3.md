## 1. 選択中とは別のプロジェクトの監査ログをExportする

Exportボタンから `apiFetch()` でBlobを取得してダウンロードする形に変えるだけで局所的に修正できます。

## 2. Review前に検収チェックを付けると、後から再確認なしでDoneへ確定できる

**何が問題か**

Doneへの更新自体には「現在Reviewかつ `checked_at` あり」という不変条件がありますが、`checked_at` を付けるAPIには現在のstatusやゴミ箱状態の検証がありません。Todoの段階でチェックを付け、後からReviewへ移すとチェックが保持され、そのまま確定APIを通せます。意図されている「Reviewに置く → 人が検収する → Doneへ確定」の順序を迂回できます。

`POST /api/tasks/:id/checked` で、ゴミ箱に無いReviewタスクだけを許可して409または400を返すようにすれば、小さな変更で塞げます。

**再現条件**

1. Todoのタスクに `POST /api/tasks/<id>/checked`、本文 `{"checked":true}` を送る。
2. `PATCH /api/tasks/<id>`、本文 `{"status":"review"}` を送る。
3. タスクの `checkedAt` が残っていることを確認する。
4. `POST /api/tasks/approve` にそのIDを渡すと、Reviewに入ってから検収していなくてもDoneへ確定される。

## 3. ログイン設定の保存が403でも「保存しました」と表示する

**何が問題か**

ログイン設定画面はGET/POSTのHTTPステータスを確認せず、403のエラーJSONも成功レスポンスとして処理します。特にPOST後は必ず保存時刻をセットするため、権限が無く設定が一切変わっていない場合でも「保存しました」と表示されます。利用者は認証設定が反映されたと思い込み、認証を有効化した時点で想定外の許可リストのまま運用する可能性があります。

共通の `json()` ヘルパーと同様に `res.ok` を確認し、失敗時はエラー表示して成功表示を出さないようにするだけで修正できます。

**再現条件**

1. 許可メールが既に1件以上設定された環境を、`CHATBAN_AUTH=off` でリモート端末から未ログインのまま開く。
2. 設定画面でログイン設定を変更し「保存」を押す。
3. サーバーは `POST /api/settings/auth` に403を返す。
4. DBは変わらないが、画面には「保存しました」と表示される。

## 4. 空の許可リストに関する説明が現在の実装と逆になっている
