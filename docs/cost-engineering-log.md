# ChatBan コストエンジニアリング実録 — 1日で1ターン8円を0.2円にした話

作成: 2026-08-09 (Day2) / 対象: AI HACK 2026 提出作品 ChatBan
すべて実測値。再現用スクリプトは `backend/scripts/` にあり。

## TL;DR

| 段階 | 1ターンのコスト | レイテンシ | 主な施策 |
|---|---|---|---|
| 朝: Sonnet固定・全部盛りプロンプト | 3〜8円 | 5〜13秒 | — (初期実装) |
| 昼: Haiku固定 + 構造ダイエット | 1〜3円 | 3秒前後 | Doneアーカイブ / 索引化 / ツール説明圧縮 |
| 夕: gpt-5.4-mini + キャッシュ | **0.2〜0.3円** | **0.9〜1.5秒** | 自動キャッシュ + 静的前置 + 軽量トークナイザ |

**約20分の1**。品質(委任割り振りの理由の質)は各段階で検証し維持。

この最適化はどれも「たまたま」ではなく、**コスト計測を初日から組み込んだ**(llm_callsテーブルに全呼び出しのトークン・ルーティング先・所要時間を記録)ことで構造が見え、次の一手が導かれた連鎖である。

---

## 発見1: コストは入力支配型 (95%が入力)

Day2昼時点の実測: 125呼び出しで入力613k tk / 出力43k tk。

原因は構造的:
- 毎ターン、システムプロンプトにボード全状態+割り振り履歴+前提を埋め込む
- ツールループのラウンドごとに会話全体を再送する
- ツール定義スキーマ(9本)が毎呼び出し約4k tkの「隠れ固定費」

**教訓: チャット駆動ツールの原価は出力ではなくコンテキスト再送で決まる。**
事業的な含意: チーム利用で月1〜2万円規模になり得る。競合SaaS価格($16/月)と並べると、コスト工学は「最適化」ではなく事業成立条件。

## 発見2: アーカイブは UX であり圧縮でもある

Done列の肥大問題(AIワーカー参加で完了速度が人間の数倍になる)への解として実装した「完了→即アーカイブ→要約カードに合流」(docs/done-archive-design.md)は、副次的にプロンプト圧縮としても機能した。Done 18件(~2k tk)が要約4行に蒸留される。

ただし実測では、アーカイブ直後もボード成長(新規タスク追加)が削減を上回り平均入力は増えた。
**教訓: 最適化はボードの成長と競争する。単発の削減より構造(増えても線形に効く仕組み)が要る。**

## 発見3: 「操作するものは索引、読むだけのものは散文」

タスク詳細の常駐をやめ、2層に分離:
- **索引**(id/title/status/assignee)のみ常駐 — タイトルが要約品質なので参照解決はこれで足りる(「タイトル=要約」原則)
- **詳細**(理由・経緯メモ・日付)は `get_task_details` ツールで遅延取得

効果: ボード部分 4.3k→1.3k tk。ping実測 8,433→6,353tk(-25%、旧形式比で実質半減)。
あわせて割り振り履歴を10件+30字に圧縮、ツール定義の説明文から行動ルールと重複する分を削った。

**教訓: 頻繁に要るデータの遅延化は逆効果(ラウンドが増えて再送が増える)。「毎ターン要る最小の索引」と「たまに要る詳細」の切り線を見極める。**

## 発見4: ルーティングの用途適性 (55モデル分散の観測)

`orcarouter/auto` に全面依存する実験を半日実施。約70呼び出しが**55種類のモデルにほぼ1回ずつ分散**し、gpt-5-proに当たった回は103.7秒。固定(sonnet=5.1s/haiku=3.0s)との対比で用途適性が実測で判明した。

確定した戦略:
- **対話** = 応答速度が生命線 → 固定モデル
- **要約の要素分解** = 品質が肝・非同期でレイテンシ許容 → ルーティング委任 (autoに34秒かかっても問題ない)
- **定型**(タイトル生成等) → コスト優先ルーティング

モデルIDを1行変えるだけでこの実験が半日で回せたのはルーター(OrcaRouter)の利点。同一機能内で品質優先と
コスト優先が並走する構成(アーカイブ要約)は、purpose別のコスト内訳として計測済み。

## 発見5: プロンプトキャッシングはプロバイダの設計思想で明暗が分かれる

同一の大きなプロンプトを2連投する比較実験(`scratchpad/cache-test.mjs` 相当):

| モデル(OrcaRouter経由) | 2回目のヒット | 実請求額 1回目→2回目 | 割引 |
|---|---|---|---|
| openai/gpt-5.4-mini | 7,424/7,844 (95%) | $0.0060 → **$0.0009** | **85%減** |
| deepseek/deepseek-chat | 8,960/9,037 (99%) | $0.0013 → $0.0002 | 86%減 |
| anthropic/claude-haiku-4.5 | **0 (不発)** | $0.0109 → $0.0109 | なし |

- OpenAI/DeepSeekの**自動キャッシュ**(プレフィックス一致で勝手に効く方式)は、アグリゲータ経由でも素通しで実額に割引が乗る
- Anthropicの**明示方式**(`cache_control`ブロックをリクエストに付ける)は、OpenAI互換フォーマットに運ぶ口がなく不発。Anthropic流のcache_controlをボディに埋める追試も無視された(OrcaRouterのusageに `claude_cache_creation_5m_tokens` という配管の痕跡はあるが常に0 — 将来対応の余地はありそう)

**教訓: ルーター経由で使うなら、キャッシュ方式が自動のプロバイダを選ぶとコスト構造が変わる。**

### 実装 (#49)

1. 対話モデルを `openai/gpt-5.4-mini` に固定
2. システムプロンプトを**静的前置・動的後置**に再構成 — キャッシュはプレフィックス一致なので、人格/行動ルール/設計思想を先頭に固定し、ボード索引/履歴/要約カードを末尾へ
3. `llm_calls` に `cached_tokens` 列を追加して継続計測

効果(実測): **異なる質問同士でもヒット率86%**(静的プレフィックスが全リクエスト共通のため)、レイテンシ0.9〜1.5秒、1ターン0.2〜0.3円。
副収入: GPT系トークナイザは日本語を効率的に数え、同一内容の入力が約4割軽くなった(6.3k→3.7k)。

## 発見6: イベントログ型プロンプト + TTL意識の再ベースライン (#50 実装済み)

**設計** (`backend/src/promptState.ts`):
- ボード状態を「基準スナップショット(バイト不変) + 変更イベントの追記」で構成し、プレフィックスを不変に保つ(公式ベストプラクティス「システムプロンプトは凍結、動的コンテキストは後方へ」と一致)
- 差分はリクエスト時にDB比較で算出 — チャット外(REST/MCP)起因の変更も同じ仕組みで拾える
- **最終リクエスト時刻を管理し、キャッシュTTL(5分)を過ぎていたら — どうせコールドなので — その瞬間に再ベースライン(先頭再構成・圧縮)**。イベント40件超・日付変化でも再ベースライン。温かい間は追記のみ
- キャッシュを「制約」ではなく「圧縮タイミングのスケジューラ」として使う

**実測** (実装直後の検証):
| ケース | cached/prompt |
|---|---|
| 再ベースライン直後(コールド) | 0/4,070 |
| 同一状態で連投 | 3,712/4,070 (91%) |
| **ボード変更後**の別会話(履歴54件) | **3,712**/4,876 — 基準部分までヒット。旧方式なら索引先頭(~2,176)で切断されていた |
| 同一ターンの2ラウンド目 | 4,736 (システム+会話履歴まで到達) |

この「溜まったら蒸留して畳む」は、Doneアーカイブの要約カード・過去ログ整頓と同じ思想の3回目の再登場。ChatBanの設計原則として一般化できる: **生データは保持し、文脈に載せるものは蒸留し、蒸留のタイミングはコスト境界で決める。**

余談: 完了検収フロー(#57/#60)でも同じ構造が出た — Review列で完了を溜めて一括検収すると要約再生成(LLM呼び出し)が1回で済む。「列の意味論がLLM呼び出し回数と一致する」例。

## 再現方法

```bash
cd backend
node scripts/cost-report.mjs        # purpose別・ルーティング先別の集計
node scripts/prompt-breakdown.mjs   # システムプロンプトのセクション別サイズ
node scripts/before-after.mjs       # アーカイブ前後の入力トークン比較
```

計測の元データは `llm_calls` テーブル(全LLM呼び出しの purpose / model / routed_model / prompt_tokens / completion_tokens / cached_tokens / elapsed_ms)。OrcaRouterコンソールのリクエストログと突き合わせ可能。
