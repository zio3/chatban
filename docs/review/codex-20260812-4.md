## 1. 監査Exportにセッション署名鍵が平文で含まれる

**何が問題か**

セッションCookieの署名に使う `auth.sessionSecret` は管理DBの `settings` テーブルへ保存されます。監査Exportはこのテーブルを無条件に全行出力するため、一度でもセッションが発行された環境では、ダウンロードしたJSONに署名鍵そのものが平文で入ります。

この鍵を入手した人は任意のメールアドレス・名前・有効期限を持つCookieを自分で署名できます。許可リスト上のメールアドレスも同じExportに含まれるため、認証必須モードでも許可ユーザーとしてセッションを偽造できます。また、検証用にExportファイルを共有しただけで、以後のセッションまで危険になります。

Export時に `auth.sessionSecret` を除外または固定文字へ置換するだけで局所的に修正できます。

**再現条件**

1. Googleログインを一度成功させ、セッションCookieを発行する。
2. 監査画面から「全ログExport」を実行する。
3. JSONの `settings` 配列に `key: "auth.sessionSecret"` と64文字の値が含まれることを確認する。
4. その値で任意のセッションpayloadへHMAC-SHA256署名を付けると、サーバーのCookie検証を通せる。

**該当ファイル:行**

- `backend/src/auth.ts:27-44`
- `backend/src/index.ts:491-495`
- `backend/src/db.ts:581-594`

## 2. 存在しないプロジェクトを指定したSocketが既定プロジェクトの更新を受信する

**何が問題か**

RESTは明示されたプロジェクトIDが存在しなければ400で拒否しますが、Socket.IOは明示値が不正または存在しない場合に「プロジェクト指定なし」と同じ扱いへ落とし、activeプロジェクトのroomへ参加させます。

そのため `/p/999999` を開くと、最初のREST読み込みは失敗する一方、別クライアントがactiveプロジェクトを更新した瞬間に `board:changed` が届き、存在しないプロジェクトのURL上へactiveプロジェクトのタスクが表示されます。RESTとSocketで境界が食い違い、誤認したまま別プロジェクトの内容を閲覧することになります。

接続クエリに `project` が明示されている場合は、存在しなければ接続を拒否するか、少なくともどのroomにも参加させないようにするだけで修正できます。

**再現条件**

1. activeプロジェクトをAにする。
2. 別タブで存在しないURL `/p/999999` を開く。
3. `/api/board` は400になり、画面には読み込み失敗が表示される。
4. Aを開いた別クライアントでタスクを追加・更新する。
5. `/p/999999` のタブがAの `board:changed` を受け取り、Aのボード内容を表示する。

## 3. ゴミ箱へ移した未完了タスクが担当負荷とプロジェクト件数に残る

**何が問題か**

通常のボード一覧は `trashed_at IS NULL` でゴミ箱タスクを除外しますが、担当者ごとの未完了件数とプロジェクト一覧の未完了件数には同じ条件がありません。Todo・In Progress・Reviewのタスクをゴミ箱へ移しても件数が減らず、見えているボードと数字が食い違います。

担当負荷はLLMのシステムプロンプトにも入り、割り振り判断の材料になります。そのため、削除済みタスクが多い担当者をAIが「負荷が高い」と誤認し、別の人へ割り振る実害もあります。

2つのCOUNTクエリへ `trashed_at IS NULL` を追加し、担当負荷側はボードと同じく `archived = 0` も揃えるだけで修正できます。

**再現条件**

1. 担当者Aに未完了タスクを1件割り当てる。
2. 設定画面のプロジェクト一覧で「未完了1件」と表示され、チャットの担当負荷でもAが1件になることを確認する。
3. そのタスクをゴミ箱へ移す。
4. ボードからは消えるが、プロジェクト一覧は「未完了1件」のままで、次のLLM呼び出しにもAの担当数1件として渡る。
