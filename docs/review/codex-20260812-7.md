## 1. 内蔵チャットに公開されている `restore_tasks` が実装されておらず、チャットから復元できない

- **何が問題か**: 内蔵チャットのツール一覧とゴミ箱画面向けプロンプトには `restore_tasks` が公開されているが、ツール実行の `switch` に対応する分岐がない。LLMが指示どおり復元ツールを呼んでも `default` の `unknown tool` が返り、画面が案内している「チャットで戻せる」が成立しない。MCP側には同名ツールが実装されているため、入口によって機能が食い違っている。
- **再現条件**: タスクをゴミ箱へ移し、内蔵チャットで「#IDを戻して」と依頼する。システムプロンプトに従って `restore_tasks` が呼ばれるが、`execTool()` は `{ error: "unknown tool: restore_tasks" }` を返し、タスクはゴミ箱に残る。`delete_tasks` と同じ位置へ `restoreTask()` を呼ぶ分岐を追加すれば小さく修正できる。
- **該当ファイル:行**: `backend/src/chat.ts:240-262`、`backend/src/chat.ts:394-484`、`backend/src/chat.ts:624-628`（実装済みのMCP側は `backend/src/mcp.ts:188-198`）

## 2. 新規プロジェクトを作成しても、同じ画面のヘッダーと他のタブへ追加が反映されない

- **何が問題か**: プロジェクト作成APIだけが `project:changed` を配信しない。設定コンポーネントは作成後に自分のローカル一覧だけを再取得するため、設定一覧には新規プロジェクトが出る一方、親の `App` が持つヘッダー用一覧は古いままになる。他のタブも更新を受け取れない。画面の説明にある「ヘッダーのプロジェクト選択から移動」が、再読み込みするまで使えない。
- **再現条件**: 設定画面で新しいプロジェクトを作成し、設定一覧とヘッダーのセレクトを比較する。設定一覧には直ちに表示されるが、ヘッダーの選択肢には追加されない。別タブの設定一覧にも追加されない。作成成功後に、更新・削除時と同じ `io.emit("project:changed", { projects: projectSummaries() })` を行えば修正できる。
- **該当ファイル:行**: `backend/src/index.ts:558-569`、`frontend/src/App.tsx:90-100`、`frontend/src/App.tsx:128-132`、`frontend/src/components/ProjectSettings.tsx:45-59`、`frontend/src/components/ProjectSettings.tsx:229-245`
- **深刻度**: 低

## 3. メンバーを編集しても、ボードの担当フィルターと提案チップが再読み込みまで古いままになる

- **何が問題か**: プロジェクト更新後の `broadcastBoard()` はタスクとサマリーカードしか配信せず、`App` の `project:changed` ハンドラーもプロジェクト一覧を置き換えるだけで `members` を更新しない。設定画面内のプロジェクト一覧だけは独自に再取得されるため、保存成功に見えるが、ボードへ戻ると追加したメンバーが担当フィルターに出ず、メンバー0人から追加した場合は「未割り当てを振る」提案も出ない。
- **再現条件**: メンバー0人のプロジェクトで設定画面を開き、メンバーを1人追加して保存し、そのままボードへ戻る。設定一覧には追加した名前が表示されるが、ヘッダーの担当フィルターは非表示のままで、未割り当てタスクがあっても割り振り提案は出ない。ページを再読み込みすると初めて反映される。`board:changed` に `members` を含めて受信側で更新するか、現在のプロジェクトが更新されたときだけ `reload()` すれば局所的に直せる。
- **該当ファイル:行**: `backend/src/index.ts:225-229`、`backend/src/index.ts:584-605`、`frontend/src/App.tsx:28-30`、`frontend/src/App.tsx:118-139`、`frontend/src/App.tsx:289-317`
- **深刻度**: 中

## 4. 別タブで表示中のプロジェクトを削除すると、そのタブに削除前のボードが残り続ける

- **何が問題か**: プロジェクト削除は全クライアントへ新しい一覧を配信するが、受信側は一覧を保存するだけで、現在のURLが削除済みになったことを処理しない。削除されたプロジェクトのSocketも旧roomへ接続したままで、ボードの最終スナップショットが画面に残る。その後のREST操作は `X-ChatBan-Project` が存在しないため400になり、表示は操作できない古いデータになる。
- **再現条件**: タブAでプロジェクトA、タブBで削除可能なプロジェクトBを開く。タブAの設定からBを削除する。タブBはURL `/p/BのID` と削除前のタスクを表示し続け、カードを移動すると `project #B not found` で失敗する。`project:changed` 受信時に現在のIDが一覧から消えていたら、既定または先頭の有効プロジェクトへ遷移させれば小さく修正できる。
- **該当ファイル:行**: `backend/src/index.ts:192-214`、`backend/src/index.ts:608-615`、`frontend/src/App.tsx:122-139`、`frontend/src/project.ts:26-39`
- **深刻度**: 中

## 5. 無効化済みプロジェクトを既定プロジェクトとして再指定でき、直前に塞いだ不可視状態を別経路から作れる

- **何が問題か**: 既定プロジェクト自身を無効化する操作は拒否されるようになったが、`setActiveProjectId()` は対象が存在するかしか確認せず、既に無効化済みかを確認しない。そのため、別のプロジェクトを無効化した後にactivate APIを呼ぶと、ドロップダウンから隠れたプロジェクトが既定になり、ヘッダー指定のないRESTやSocketの追従先として書き込まれる。削除も「既定なので不可」となり、「見えない・消せない・でも書き込まれる」状態が迂回して再発する。
- **再現条件**: 既定でないプロジェクトBを `PATCH /api/projects/B` の `{ "archived": true }` で無効化し、続けて `POST /api/projects/B/activate` を呼ぶ。どちらも成功し、Bは通常のドロップダウンに出ないまま既定になる。`setActiveProjectId()` で `row.archived` を確認して409相当で拒否すれば小さく修正できる。
- **該当ファイル:行**: `backend/src/store.ts:343-357`、`backend/src/store.ts:431-438`、`backend/src/index.ts:571-581`
- **深刻度**: 中
