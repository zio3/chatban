## 1. `/p/0` が存在しないプロジェクトではなく既定プロジェクトとして扱われる

- **何が問題か**: URLから得たプロジェクトIDを真偽値で判定しているため、数値の `0` だけが「プロジェクト指定なし」に変換される。RESTの `X-Project-Id` とSocketの `projectId` が送られず、存在しない `/p/0` を開いているのに既定プロジェクトのデータが表示され、そのまま既定プロジェクトへ書き込める。バックエンド側にある未知プロジェクトの拒否処理にも到達しない。
- **再現条件**: `/p/0` を直接開き、タスク一覧を表示するかタスクを追加する。URLは `/p/0` のままだが、既定プロジェクトの一覧が表示され、追加内容も既定プロジェクトに保存される。`projectIdFromUrl()` が返す `0` を `id ? ... : {}` で判定していることが原因。`id !== null` で判定するか、URL解析時に非正数を無効なIDとして明示的に扱えば小さく修正できる。
- **該当ファイル:行**: `frontend/src/project.ts:12-20`、`frontend/src/socket.ts:7-8`（参考: バックエンドの拒否処理は `backend/src/index.ts:128-137`、`backend/src/index.ts:191-212`）
- **深刻度**: 中

## 2. 担当者フィルターで隠れた未完了の依存タスクが「解決済み」と判定される

- **何が問題か**: ボードへフィルター後のタスク配列だけを渡し、その配列から依存先の存在と未完了状態も計算している。そのため、表示対象タスクが別担当者の未完了タスクに依存している場合、依存先がフィルターで消えた瞬間に未解決判定からも消え、依存関係の表示が実態と逆になる。依存先のタイトルも引けなくなる。
- **再現条件**: Alice担当のタスクAを、Bob担当の未完了タスクBに依存させる。担当者フィルターでAliceだけを選ぶ。Aは表示される一方、Bは表示配列から除かれるため、Aの依存表示はBを未解決として扱わず、依存先の情報も欠落する。描画対象はフィルター後の配列のまま、依存判定用の索引だけ全タスクから作って渡せば小さく修正できる。
- **該当ファイル:行**: `frontend/src/App.tsx:309-323`、`frontend/src/App.tsx:486-495`、`frontend/src/components/Board.tsx:98-103`、`frontend/src/components/Board.tsx:138-145`、`frontend/src/components/Board.tsx:398-402`
- **深刻度**: 中

## 3. アーカイブ済みタスクをゴミ箱経由で完全削除でき、サマリーカードだけが壊れた参照として残る

- **何が問題か**: `trashTask` は `archived` を確認せず、IDさえ一致すればアーカイブ済みタスクもゴミ箱へ移す。チャット/MCPの削除操作もこの関数を呼ぶため、通常UIに見えないアーカイブ済みタスクを指定して削除できる。その後ゴミ箱から完全削除するとタスク本体は失われる一方、サマリーカードの `task_ids` は更新されず、カードに存在しないタスクIDが残る。検収・アーカイブ済み成果の監査元も失われる。
- **再現条件**: タスクをDoneへ移し、チェック・承認してアーカイブする。タスクチャットまたはMCPからそのIDの削除を依頼し、ゴミ箱で完全削除する。サマリーカードにIDが残るが、そのタスクを開くと404になる。凍結前の最小修正なら、`trashTask` の更新条件へ `archived = 0` を追加してアーカイブ済みタスクの削除を拒否できる。
- **該当ファイル:行**: `backend/src/db.ts:228-256`、`backend/src/db.ts:370-406`、`backend/src/chat.ts:408-413`、`backend/src/mcp.ts:175-184`
- **深刻度**: 中

## 4. 一度監査クエリを実行したプロジェクトは、Windows上で削除に失敗する

- **何が問題か**: 監査用クエリはプロジェクトDBを読み取り専用で開き、`roHandles` に保持する。一方、プロジェクト削除前の `closeProjectDb()` は通常の `handles` しか閉じず、読み取り専用ハンドルを残したままDBファイルを `renameSync` する。Windowsでは開いているSQLiteファイルの移動が `EBUSY` になり、削除APIが400を返す。プロセス再起動までそのプロジェクトを削除できない。
- **再現条件**: 既定ではないプロジェクトに対して `query_log` の `audit` スコープを一度実行し、そのプロジェクトを削除する。読み取り専用ハンドルが残っているためファイル移動が失敗する。Windows上の一時DBでも、読み取り専用の `better-sqlite3` ハンドルを開いた状態では `renameSync` が `EBUSY` になることを確認した。`closeProjectDb()` で同じIDの `roHandles` もcloseして削除すれば小さく修正できる。
- **該当ファイル:行**: `backend/src/store.ts:368-386`、`backend/src/store.ts:429-441`、`backend/src/store.ts:645-660`、`backend/src/db.ts:861-865`
- **深刻度**: 中
