## 1. 認証必須モードではログイン成功後もボードとSocket接続が復旧しない

**何が問題か**

アプリ起動時、認証状態の取得とは別に `reload()` と `loadProjects()` が即座に実行され、Socket.IOもモジュール読み込み時に接続を開始します。`CHATBAN_AUTH=on` で未ログインなら、ボード・プロジェクト一覧は401になり、Socket接続も認証ミドルウェアで拒否されます。

Googleログイン成功後に呼ばれるのは `loadAuth()` だけです。失敗済みの `reload()` と `loadProjects()` は再実行されず、Socketに対する `socket.connect()` もありません。Socket.IOはnamespaceミドルウェアによる `connect_error` の後、自動的には再接続しないため、ログイン画面を抜けてもボードは初回401のエラー／空状態のままで、プロジェクト一覧とリアルタイム更新も復旧しません。ブラウザを再読み込みすると直ります。

逆方向も同様で、ログアウト時はCookieとReact上の認証状態だけが消え、接続済みSocketを `disconnect()` していません。認証必須モードでログイン画面へ戻った後も、そのページが保持している既存Socketは切断されるまで配信を受けられます。

修正はログイン成功時に `reload()`、`loadProjects()`、`socket.connect()` を呼び、ログアウト時に `socket.disconnect()` を呼ぶだけで局所的に対応できます。あるいは認証ユーザーの変化を監視する `useEffect` にまとめられます。

**再現条件**

1. `CHATBAN_AUTH=on` で、Cookieのないブラウザからアプリを開く。
2. 初回の `/api/board` と `/api/projects` が401、Socket.IOが `connect_error` になる。
3. Googleログインを成功させる。
4. ログイン画面は消えるが、ボード／プロジェクト一覧／Socket接続が復旧しないことを確認する。
5. ブラウザを再読み込みすると表示・リアルタイム更新が復旧する。

ログアウト側は、ログイン済み画面でSocket接続を確立した後にログアウトし、別クライアントでボードを更新すると、ログイン画面の背後で既存Socketのイベントリスナーが動き続けることで確認できます。

## 2. REST APIが未定義のstatusを保存でき、タスクがボードから消える

**何が問題か**

TypeScript上の `TaskStatus` は4値に限定されていますが、RESTリクエストは実行時検証されません。タスク作成APIは `req.body.status` をそのまま `createTask()` に渡し、`createTask()` が特別扱いするのは `done` だけです。更新APIも任意の文字列を `updateTasks()` まで通せます。

例えば `status: "banana"` を保存すると、ボードは4つの既知ステータスでしかタスクを抽出しないため、そのタスクはどの列にも表示されません。チャットの `#ID` リンク等から詳細パネルを開いた場合は、`STATUS_LABELS[task.status]` が `undefined` となり、`status.cls` の参照で画面が例外になります。

作成・更新RESTの入口で4値を検証して400を返すだけで修正できます。DB層でも未知のstatusを拒否すれば、将来別の入口が増えても同じ事故を防げます。

**再現条件**

次のいずれかを実行します。

```http
POST /api/tasks
Content-Type: application/json

{"title":"表示されないタスク","status":"banana"}
```

```http
PATCH /api/tasks/123
Content-Type: application/json

{"status":"banana"}
```

レスポンスおよびDBには `status: "banana"` が保存されますが、ボードのTodo／In Progress／Review／Doneのどこにも表示されません。該当タスクの詳細を開くとステータス表示で例外になります。

## 3. 存在しないタスクの専用チャットでもLLMを呼び、孤児ログを保存する

**何が問題か**

`POST /api/tasks/:id/chat` は対象タスクの存在確認をしません。`runChatTurn()` 側では存在しないIDなら `taskFocus` が `undefined` になるだけなので、通常チャットに近い状態で有料のLLM呼び出しが実行されます。その後、外部キー制約のない `chat_messages.task_id` に存在しないIDを付けて会話ログを保存します。

削除・プロジェクト切替・古い画面などでタスクが消えた直後に送信すると、ユーザーには対象タスクの会話に見える一方、AIには対象タスクの詳細が渡らず、返答や更新が意図しない内容になり得ます。存在しない数値IDなら孤児ログも残ります。LLM呼び出し前に `getTask(taskId)` を確認して404を返すだけで修正できます。

**再現条件**

存在しないIDに対して次を送ります。

```http
POST /api/tasks/999999/chat
Content-Type: application/json

{"message":"このタスクを進めて"}
```

404にならずLLM処理が開始され、成功時には `task_id = 999999` の会話ログが保存されます。数値でないIDでは、LLM呼び出し後のDB保存段階で500になる可能性があり、応答を返せないのにLLMコストだけが発生します。

**該当ファイル:行**

- `backend/src/index.ts:394-430`
- `backend/src/chat.ts:732-740`
- `backend/src/store.ts:140-147`

**深刻度**

## 4. 存在しないプロジェクトへのPATCHが404ではなく500になる

**何が問題か**

`PATCH /api/projects/:id` はURL上のプロジェクトIDが存在するか確認しません。名前変更とアーカイブ変更はSQLの更新件数0で静かに通りますが、その後の `broadcastBoard(id)` が `withProject(id)` で例外を投げるため、結果は500になります。`members` を含む場合は `setProjectMembers()` 内で先に例外になります。

設定画面を古いタブで開いたまま別タブからプロジェクトを削除した場合など、通常操作の競合でも発生します。ハンドラー冒頭で `getProject(id)` を確認して404を返すだけで直せます。

**再現条件**

存在しないプロジェクトIDに対して次を送ります。

```http
PATCH /api/projects/999999
Content-Type: application/json

{"name":"変更後"}
```

期待される404ではなく、`broadcastBoard(999999)` またはDB取得時の例外により500になります。
