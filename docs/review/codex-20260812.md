## 1. 検収API以外のREST経路からDoneへ直接遷移できる

**何が問題か**

`POST /api/tasks/approve` にはReview列・検収チェック・生存状態のサーバー側検証が追加されましたが、通常のタスク作成・更新APIは任意の `status` をそのままDB層へ渡しています。そのため、`POST /api/tasks` または `PATCH /api/tasks/:id` から `status: "done"` を指定すると、`approveChecked()` を経由せず、検収チェックなしでDoneへ移動できます。`updateTasks()` はこの遷移を完了として扱い、アーカイブ処理も起動します。

「Doneへ至る唯一の扉は検収API」という不変条件がAPI全体では成立していません。UIが通常この値を送らないことに依存しており、古いクライアント、将来のUI変更、直接API呼び出しで破れます。

**再現条件**

次のいずれかを実行します。

```http
POST /api/tasks
Content-Type: application/json

{"title":"未検収タスク","status":"done"}
```

または、Todo／In Progress／未チェックのReviewタスクに対して次を実行します。

```http
PATCH /api/tasks/123
Content-Type: application/json

{"status":"done"}
```

いずれも `POST /api/tasks/approve` を通らずDoneになります。

## 2. 許可リストから外したユーザーの接続済みSocket.IOセッションが失効しない

**何が問題か**

Socket.IOの認証はハンドシェイク時にのみ行われます。接続後、管理者がユーザーを許可リストから削除しても、すでに接続しているSocketは再認証・切断されません。そのユーザーはREST APIへ新しくアクセスできなくなっても、既存Socketを維持している限り `board:changed`、`project:changed`、`archive:working`、`chat:progress` などの配信を受け続けられます。

Cookieの再検証と新規Socket接続の拒否は実装されていますが、既存の長寿命接続まで失効させないと、許可リスト変更によるアクセス剥奪が完全には成立しません。

**再現条件**

1. 許可リストに登録されたユーザーとしてSocket.IOへ接続する。
2. 接続を維持したまま、別の管理者セッションからそのメールアドレスを許可リストから削除する。
3. 別クライアントでボードを更新する。
4. 削除済みユーザーの既存Socketが引き続き `board:changed` を受信する。

## 3. 許可リストを空文字で保存すると認証がfail-openになる

**何が問題か**

`isAllowed()` は空のリストを初回セットアップ状態として扱い、すべてのメールアドレスを許可します。一方、認証設定APIは `allowedEmails: ""` を有効な更新として保存できます。「設定がまだ存在しない」と「管理者が明示的に全員を削除した」が区別されていません。

このため、管理者が許可メールをすべて削除すると、現在有効な署名済みCookieを持つユーザーが再び許可されます。また、次にGoogleログインしたユーザーが初回ユーザーとして許可リストへ登録され、オーナーになれます。権限を全削除する操作が、逆に認証を開放する結果になります。

**再現条件**

1. 許可リストに複数ユーザーを登録し、それぞれログインして署名済みCookieを取得する。
2. 管理者が `POST /api/settings/auth` に `{"allowedEmails":""}` を送る。
3. 以前のCookieで保護対象APIへアクセスする、または別のGoogleアカウントでログインする。
4. 空リストが初期状態として扱われ、既存セッションが通るか、新しいアカウントがオーナー登録される。

**該当ファイル:行**

- `backend/src/auth.ts:69-90`

## 4. 不正なCookie値でSocket.IO認証処理が同期例外を送出する

**何が問題か**

Socket.IO用の `userFromCookieHeader()` は、Cookie値に対して `decodeURIComponent()` を例外処理なしで呼び出します。不正なパーセントエンコードを含むCookieでは `URIError` が発生します。Socket.IOのnamespaceミドルウェアは登録関数の同期例外を捕捉しないため、認証失敗として処理されず、Node.jsプロセスの未捕捉例外になる可能性があります。

レビュー時に関数を直接呼び出し、次の結果を確認しました。

```text
URIError: URI malformed
```

認証有効時に未認証の外部クライアントから到達できるため、サービス拒否につながります。

**再現条件**

`CHATBAN_AUTH=on` で起動し、Socket.IOのハンドシェイクへ次のCookieヘッダーを送ります。

```http
Cookie: chatban_session=%E0%A4%A
```

または現在の関数を直接呼び出します。

```ts
userFromCookieHeader("chatban_session=%E0%A4%A");
```

`decodeURIComponent()` が `URIError: URI malformed` を送出します。

**該当ファイル:行**

- `backend/src/auth.ts:135-143`
- `backend/src/index.ts:141-149`

**深刻度**
